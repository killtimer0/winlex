# GUI 测试维护

执行、依赖与远程调度见 [构建与验证](../../docs/build.md#测试与独立验证)。桌面测试默认只在远程目标执行。

## 编写场景

- 场景表达用户操作与可观察结果：查找、阅读、导航、来源管理、设置、窗口和外观。
- 共享操作属于 `driver/`；测试模块不是其他测试或 fixture 的依赖。只在本场景使用的辅助逻辑留在本地。
- `support/` 提供 Windows 原语与执行基础设施。驱动可以使用它，不得反向导入场景。
- 断言针对产品契约，不以当前控件组织、实现调用或日志形状作为正确性的依据。原生可访问性、输入与呈现契约可以直接测量相应 Windows 行为。
- 真实输入场景标记 `interactive`，通过 `run.py --desktop current --real-input` 执行；不得绕过输入所有权或恢复账本。
- 修改全局高对比度的场景必须先注册独立恢复 watchdog，并提供目标机的 `--hc-theme` 预期外观文件。

## 执行与失败边界

| 责任方 | 拥有的契约 |
| --- | --- |
| `support.execution` 协调器 | 整轮绝对预算、取消、继续条件、汇总与最终 `run.json` |
| `support.custody` 单次资源托管进程 | pytest job、独立桌面、输入所有权、进程树停止与资源恢复 |
| pytest fixture 与生命周期插件 | 场景执行、合作式关闭、阶段与操作证据 |
| 独立 HC watchdog | 托管进程或 pytest 被终止后的全局外观恢复及任务清理凭据 |

单次托管进程只等待 pytest 退出或协调器的停止请求，不决定重试。协调器必须等托管进程退出并验证清理证据，才可以继续或发布完成结果。终止进程不等于确认输入和外观恢复。

每个 pytest 进程只写一份 `events.jsonl`，进度和耗时从该记录派生；托管进程使用独立的 `runner-events.jsonl`，两者描述不同故障边界。清理计划具有固定截止时间，不能由后续操作续期。

## 验证执行框架

`tests/scripts/test_gui_deadlines.py` 与 `test_gui_remote.py` 通过公开入口启动真实进程，用阻塞、取消、进程终止和清理失败验证契约，不替换私有执行函数。故障探针及日志保留在 `tmp/`。

按风险选择定向场景和故障契约；分别报告通过、跳过与未验证。高对比度恢复与 XP 原生消息阻塞须独立验证，不能由普通场景通过推定。
